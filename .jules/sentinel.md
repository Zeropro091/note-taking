## 2024-06-27 - Path Traversal Protection via Strict Rejection and Normalization
**Vulnerability:** Path traversal attacks were possible because the `validateNoteId` function did not explicitly reject inputs containing `..` and relied only on `path.relative` check without first normalizing Windows backslashes to forward slashes. This could lead to a POSIX path traversal bypass where `..\\` might be misinterpreted on POSIX systems. A test case `folder/../../note` was also incorrectly allowed since it resolved inside the note directory, missing the intent to fully reject any form of path traversal characters.
**Learning:** Checking for `..` dynamically is error-prone when path resolution behaves differently based on the platform. It's safer to proactively reject any ID containing `..` entirely rather than trying to sanitize it, and to consistently normalize backslashes (`\`) to forward slashes (`/`) before resolving relative paths to prevent POSIX path traversal bypasses.
**Prevention:** Always normalize slashes before resolving user input against a base path and use defense-in-depth by explicitly rejecting identifiers containing `..` rather than just relying on `path.relative` or attempting to sanitize it away.
