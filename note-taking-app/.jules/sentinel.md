## 2026-06-05 - Fix Path Traversal Vulnerability in `validateNoteId`
**Vulnerability:** The application was vulnerable to path traversal because `validateNoteId` permitted the sequence `..` if the overall path resolved to somewhere within the base directory (e.g. `folder/../../note`). This behavior, particularly when dealing with POSIX bypasses, could potentially allow attackers to craft deceptive note identifiers to traverse the file system structure or manipulate the file structure by using unexpected path strings that resolve ambiguously or circumvent standard validation logic.
**Learning:** Resolving and checking path components relative to a root isn't inherently sufficient to stop advanced manipulation (like POSIX bypass vectors where strings containing `..` or unnormalized backslashes could manipulate routing logic before path verification). Simply checking `path.relative` handles some forms of directory breakout, but it leaves open the risk of bypasses when other checks apply naive validations to strings containing directory traversal commands.
**Prevention:** In addition to verifying the relative location with `path.relative`, ensure to normalize the path (converting backslashes `\` to forward slashes `/`) *before* resolving, and explicitly reject any path string that contains `..`. This defense-in-depth approach halts traversal sequences earlier in the string analysis phase, thus closing avenues for POSIX or other parsing bypasses.
